Your First Mechanism: The Intake

Last lesson you moved all your driving into its own room — the Drivebase class. Driving was special though: it was already written, you just reorganized it. This lesson you build a brand-new mechanism from an empty file: the intake, the roller that pulls game pieces into the robot.

And when you write it, you'll follow the exact same shape every real FTC subsystem uses. Learn it here on one motor, and the dumper, the arm, the climber — everything after this — will feel familiar.

What does an intake even do?

It's one motor with a squishy roller. Spin it one way and it grabs game pieces off the field and pulls them in. Spin it the other way and it spits a jammed piece back out. Leave it off the rest of the time so it isn't fighting or grinding. That's the whole job: three choices.

The big idea: a state machine

Notice we just described the intake as being in one of exactly three situations: pulling in, stopped, or spitting out. It is always in one of them, never two at once. When something can only ever be in one of a handful of named situations, programmers call it a state machine, and each situation is a state.

Why not just call motor.setPower() directly?

You could sprinkle motor.setPower(1.0) and motor.setPower(0) all over your OpMode. But then the “what is the intake doing right now?” answer is scattered across a dozen places, and two of them can fight each other. A state machine keeps a single source of truth: one field that always knows the answer, and one place that acts on it. Cleaner, and far easier to debug.

Our state machine has four parts, and you'll build them in order:

  • a list of the states (an enum) — the three names,
  • a field that remembers which state we're in right now,
  • command methods (forward, reverse, off) that only change the state,
  • an update() that runs every loop and makes the motor match the state.

Meet Intake.java

A new file just appeared in your project: Intake.java. Open it and read the top. The motor field, the tuning constants, and the constructor are already there for you — the constructor finds the motor in the hardwareMap (looking up the name "intake_motor" from the Driver Hub config), exactly like Drivebase found its four wheels. What's missing is the state machine. You'll add it in four parts.

Part A — Name the states (an enum)

An enum (short for enumeration) is a tiny custom type whose only values are a fixed list of names you write down. It's perfect here: the intake can be FORWARD, OFF, or REVERSE — and nothing else. Using an enum instead of, say, the numbers 0/1/2 means the compiler itself stops you from ever setting a state that doesn't exist.

▸ Intake.java : Intake : States
Type this into Intake.java⩢ Copy
public enum State {
    FORWARD,   // pulling game pieces in
    OFF,       // stopped
    REVERSE    // pushing back out to clear a jam
}

Now add the field that remembers the current state. It starts at OFF — a robot should never boot up with its intake already spinning.

▸ Intake.java : Intake : Current State
Type this into Intake.java⩢ Copy
private State state = State.OFF;   // start stopped

Part B — The command methods (change the state)

Here's the part that surprises people: the forward(), reverse(), and off() methods do not touch the motor. Each one only sets the state field. That's the whole trick of a state machine: deciding what to do and doing it are split apart. The commands decide; update() (Part C) does. getState() lets the OpMode peek at the current state.

▸ Intake.java : Intake : Commands
Type this into Intake.java⩢ Copy
/** Run the intake inward (collecting). Only changes the state. */
public void forward() {
    state = State.FORWARD;
}

/** Run the intake outward (spitting a stuck piece back out). */
public void reverse() {
    state = State.REVERSE;
}

/** Stop the intake. */
public void off() {
    state = State.OFF;
}

/** Lets the OpMode read the state -- to show it, or to decide a toggle. */
public State getState() {
    return state;
}

Part C — update(): turn the state into motor power

This is the heart of the state machine. The scheduler calls update() once every loop. It looks at state and sets the motor to match — and because it runs every single loop, the motor always reflects the current state, no matter who changed it. A switch is the clean way to handle “one behavior per state.”

▸ Intake.java : Intake : Apply State
Type this into Intake.java⩢ Copy
switch (state) {
    case FORWARD:
        motor.setPower(INTAKE_FORWARD_POWER);
        break;
    case REVERSE:
        motor.setPower(INTAKE_REVERSE_POWER);
        break;
    case OFF:
        motor.setPower(0.0);
        break;
}

The two speeds come from the named constants at the top of the file — full power (1.0) to pull in, a gentler -0.5 to un-jam. Want a different feel later? Change those two lines; nothing else.

Part E — Drive it with two buttons

Now the fun part: wiring the gamepad. We'll make A run the intake in and B run it out. And we'll add one safety rule: if the intake is already running (either direction), pressing either button just stops it. So the intake always goes in → stop → out, never slamming straight from full-forward into reverse — that protects the intake motor and the drive train.

Why we need “edge detection”

The loop runs ~50 times a second. If you just wrote if (gamepad1.a), then a single half-second press would count as dozens of presses — the intake would flicker on/off so fast you couldn't control it. Edge detection fixes this: we remember whether A was already down last loop, and only react on the loop where it goes from up to down — the rising edge, one clean press.

1. Remember last loop's buttons

▸ MecanumDrive.java : Intake : Variables
Type this into MecanumDrive.java⩢ Copy
private boolean previousA = false;
private boolean previousB = false;

2. In the loop: detect the press, then start or stop the intake

Read it slowly. pressedA is true only on the one loop where A just went down. When that happens, we ask the intake what it's doing: if it's running at all (not OFF), we stop it; only from a stop does A run it forward. B follows the same rule but runs reverse from a stop. The last two lines save this loop's buttons so next loop can compare.

▸ MecanumDrive.java : Intake : Loop
Type this into MecanumDrive.java⩢ Copy
boolean pressedA = gamepad1.a && !previousA;
boolean pressedB = gamepad1.b && !previousB;
if (pressedA) {
    if (robot.intake.getState() != Intake.State.OFF) robot.intake.off();
    else robot.intake.forward();
}
if (pressedB) {
    if (robot.intake.getState() != Intake.State.OFF) robot.intake.off();
    else robot.intake.reverse();
}
previousA = gamepad1.a;
previousB = gamepad1.b;

See how the OpMode never touches the motor either? It only sends commands — forward(), reverse(), off(). The input layer decides the gesture (press to start, press again to stop); the intake decides the power. Each side stays simple because it minds its own business. That's the pattern.

Optional: show the state on the driver station

Down near your other telemetry.addData(…) lines, you can add telemetry.addData("Intake", robot.intake.getState()); to watch the state flip live as you press the buttons. Handy for confirming the buttons work.
