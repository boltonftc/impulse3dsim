Adding a Subsystem: The Recipe

Every mechanism you've added so far (the intake, the feeder, the flywheel) followed the same steps. Once you can see those steps as a recipe, adding any new mechanism to your robot is a checklist, not a mystery. This lesson teaches the recipe first, then walks through it with a real example: an alternate pollen extractor made of two continuous-rotation (CR) servos on the front of the robot.

⚠ This is an ALTERNATIVE to the Extractor Arm lesson

The Extractor Arm lesson builds a different extractor: one positional servo that swings a bar down. This lesson builds two spinning wheels instead. A robot has one or the other, so add one of them to your code, not both. They would both want D-pad down, and one tap would run two mechanisms at once.

1. The recipe

Add any mechanism the same way, in this order:

  1. Configure the hardware. On the Driver Hub, add each device to the robot configuration with the right type and an exact name. The name is how your code finds it.
  2. Write the subsystem class (a new file). It always has the same five parts:
    • constants: named numbers to tune (powers, positions);
    • fields: the hardware, plus a state that remembers what we want;
    • a constructor: find the hardware, set directions, start safe, and survive a robot that doesn't have it;
    • commands: small methods that only change the state;
    • update(): runs every loop and makes the hardware match the state.
  3. Register it in Robot.java. A field, a line that builds it, and subsystems.add(...) so the scheduler calls its update().
  4. Map the buttons in your TeleOp. Buttons call commands; they never touch the hardware.
  5. Show it on telemetry. One line, so drivers (and you, debugging) can see the state.
  6. Use it in autonomous (if needed). The same commands, called from your auto.
  7. Test. Simulator first (does it compile and does telemetry change?), then the real robot with hands clear.
Why this order works

Each step only depends on the one before it. The configuration name is used by the subsystem; the subsystem is used by Robot; Robot is used by the TeleOp and autos. And because buttons only call commands, the TeleOp and autos never need to know how the mechanism works, only what to ask it to do.

2. The example: an alternate pollen extractor

Two CR servos sit on the front of the robot, one on each side, with grippy wheels that pull pollen in. The driver taps D-pad down to start them and taps it again to stop them. No reverse for now.

Step 1: Configure the hardware

On the Driver Hub, under Configure Robot, add both servos to free servo ports as Continuous Rotation Servo (not plain Servo), named exactly:

  • extractor_left
  • extractor_right

A positional servo is told where to go (0.0 to 1.0). A CR servo is told how fast to spin (−1.0 to 1.0), like a small motor. If you configure it as the wrong type, hardwareMap.get(CRServo.class, ...) won't find it.

Step 2: Write the subsystem, AltExtractor.java

Constants. One named number for how fast the wheels spin:

private static final double RUN_POWER = 1.0;   // full speed while running

static final means one shared value that never changes while the program runs. If the wheels pull too hard, you change this one line.

Fields. The two servos, and the state:

private final CRServo left;      // null if this robot has no alt extractor
private final CRServo right;
private boolean running = false; // does the driver WANT the wheels spinning?
  • private: only AltExtractor may touch the servos. Everyone else has to ask through a command.
  • final: each servo is found once, in the constructor, and never swapped.
  • running is the whole state. It's just on or off, so a boolean is enough. (The intake needed an enum because it had three choices. If you add reverse later, turn this into an enum.)

One subsystem, two servos. Notice we didn't make two subsystems. The two wheels always work together, so one subsystem owns both. A subsystem is a mechanism, not a single device.

The constructor.

public AltExtractor(HardwareMap hardwareMap) {
    CRServo foundLeft = null;
    CRServo foundRight = null;
    try {
        foundLeft  = hardwareMap.get(CRServo.class, "extractor_left");
        foundRight = hardwareMap.get(CRServo.class, "extractor_right");
    } catch (IllegalArgumentException e) {
        foundLeft = null;    // either one is missing: run without the extractor
        foundRight = null;
    }
    left = foundLeft;
    right = foundRight;
    if (hasExtractor()) {
        right.setDirection(DcMotorSimple.Direction.REVERSE);  // mirror-mounted
        left.setPower(0.0);                                   // start stopped
        right.setPower(0.0);
    }
}
  • try / catch. If a name isn't in the configuration, hardwareMap.get throws an IllegalArgumentException. We catch it and set both servos to null, so the extractor is either completely there or completely off. That's why the code compiles and runs in the simulator and on robots without these servos.
  • Why reverse one? The servos are mirror-mounted: the right one faces the opposite way. Given the same signal, both spin the same way as seen from their own shaft, which means one wheel pulls pollen in while the other pushes it out. Reversing the right one makes “positive power” mean “pull in” for both. You fix direction once, here, and never think about it again. On the real robot, if both wheels push out, reverse the left one instead of the right.
  • Start safe. Power 0 at INIT, so nothing spins until a driver asks.
private boolean hasExtractor() {
    return left != null && right != null;
}

Commands. They only change the state. None of them touch a servo:

public void on()     { running = true; }
public void off()    { running = false; }
public void toggle() { running = !running; }   // ! means "the opposite of"

public boolean isRunning() { return running; }

The TeleOp uses toggle(). Autos use on() and off(), because an auto needs to know exactly what state it's asking for, not “whatever the opposite of now is”.

update(), called by the scheduler every loop:

@Override
public void update() {
    if (!hasExtractor()) {
        return;                                   // no extractor on this robot
    }
    double power = running ? RUN_POWER : 0.0;     // ON: run power, OFF: stop
    left.setPower(power);
    right.setPower(power);
}

running ? RUN_POWER : 0.0 is the ternary operator: “if running is true, use RUN_POWER, otherwise use 0.0”. It's a one-line if/else that gives back a value.

Step 3: Register it in Robot.java

// with the other subsystem fields:
public final AltExtractor altExtractor;

// in the constructor, with the other subsystems:
altExtractor = new AltExtractor(hardwareMap);
subsystems.add(altExtractor);
  • Forget the new AltExtractor(...) line and it won't compile: a final field must be given a value in the constructor.
  • Forget subsystems.add(...) and it compiles but never moves: the scheduler never calls its update(), so the state changes but no power is ever sent. This is the sneakiest mistake in the recipe.

Step 4: Map the button in your TeleOp

Tap-to-toggle needs edge detection, just like the intake's A button. Add a field to the TeleOp class (outside the loop, next to previousA):

private boolean previousDpadDown = false;

And inside the loop:

boolean pressedDown = gamepad1.dpad_down && !previousDpadDown;   // true on the FIRST loop only
if (pressedDown) robot.altExtractor.toggle();
previousDpadDown = gamepad1.dpad_down;                               // remember for next loop
Why edge detection here, but not in the Extractor Arm lesson?

The loop runs about 50 times a second, so a quick tap is held for several loops. In the Extractor Arm lesson, D-pad down always means “deploy”, so saying it 10 times changes nothing. Here, a tap toggles: without edge detection, holding the button would flip the extractor on, off, on, off... every loop. pressedDown is true only on the one loop where the button is down now and wasn't last loop.

The field must live outside the loop. Declared inside, it would start over as false every loop and forget the last one.

In the simulator, the / key is D-pad down.

Step 5: Telemetry

telemetry.addData("Alt extractor", robot.altExtractor.isRunning() ? "ON" : "OFF");

In the simulator, this line is how you test the whole recipe: tap / and watch it flip between ON and OFF.

Step 6: Use it in autonomous

robot.altExtractor.on();     // start pulling pollen
// ... drive, calling follower.update() and robot.update() every loop ...
robot.altExtractor.off();    // done
robot.update();              // send it to the servos right away

Remember: on() only changes the state. The servos only start when robot.update() runs, so any waiting you do in an auto must keep calling robot.update().

Step 7: Test

  • Simulator: it compiles, INIT runs, and telemetry flips ON/OFF with each tap.
  • Real robot: hands clear. Tap D-pad down: both wheels should pull inward. Both push out? Reverse the left servo instead of the right. One pulls in and one pushes out? Your servos aren't mirror-mounted after all, so remove the reverse line. Telemetry says ON but nothing spins? Check the two configuration names and the servo type: if either is wrong, the try/catch quietly turned the extractor off.
