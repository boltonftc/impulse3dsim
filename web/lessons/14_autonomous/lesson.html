Autonomous with Pedro Pathing

Every FTC match starts with 30 seconds of autonomous: the robot drives itself, with nobody touching a controller. Up to now you have written TeleOp — you drive. Now the robot needs a plan it can run alone: go to this spot, do a thing, go to the next spot. In this lesson you write your first autonomous and watch the robot follow a path you drew for it.

TeleOp reads a gamepad; Autonomous follows a plan

A TeleOp OpMode loops forever reading sticks and buttons. An autonomous OpMode has no driver — it runs a fixed list of steps once and stops. That is why this file is marked @Autonomous instead of @TeleOp: it shows up in the autonomous slot on the Driver Hub.

A new tool arrives: the Pedro Pathing library

This lesson adds three new files to your package — SimpleAuto.java (the one you write), plus PinpointLocalizer.java and MecanumDrivetrainSubsystem.java (given, ready to read) — and for the first time your code borrows code someone else wrote. Everything you finished last lesson is still here; these files just join it. If you don't see all three in your file list yet, click Reset to Start at the bottom of this lesson to pull in this lesson's starting code.

What is a library, a .jar, and an import?

A library is a bundle of code someone else already wrote and tested, so you don't have to. Pedro Pathing is a library that knows how to steer a robot smoothly to an exact spot on the field — tricky math that would take weeks to get right. You get to just borrow it.

  • A .jar file is simply a zip of that library's code (here, pedro-core.jar). Picture it as a book you added to your shelf.
  • An import line at the top of a file — like import com.pedropathing… in the new files — is you saying “I want to use this part of that book.”
  • Needing that book on the shelf for your code to build is called a dependency: your code now depends on Pedro being there.

Behind the scenes: this simulator already keeps pedro-core.jar on its shelf, so the instant a file imports Pedro it just works — there's nothing for you to install here.

Driving to a spot is a different job than driving by hand

Steering to an exact field position is a control problem: the robot must keep checking “where am I versus where should I be?” and correct itself. That closed loop is what Pedro Pathing's Follower does for us. The Follower needs two helpers, and both are new given files in your package that you can read but do not have to write:

The Follower needs a Localizer and a Drivetrain
  • PinpointLocalizer — answers “where am I?” It wraps the same goBILDA Pinpoint your Localization subsystem uses, configured the same way, so the two never disagree.
  • MecanumDrivetrainSubsystem — answers “how do I push the wheels?” It uses the same mecanum mixing math as your TeleOp Drivebase.

Open both files and skim them. Notice there is nothing magic inside — just the sensor and the wheels you already know, wrapped so the Follower can call them. They are given because matching the exact shape Pedro asks for (its interface) is just plumbing — the interesting logic is the drive and localization code you already wrote in earlier lessons.

Your mechanisms are not new: autonomous builds the same Robot as TeleOp and calls the same robot.update() scheduler, so the dumper you wrote earlier works here unchanged.

Poses and the field frame

A Pose is the same three-number idea from the localization lesson — an (x, y) spot plus a heading — but now you use it to tell the robot where to go. And it uses the exact same field frame you sanity-checked last lesson:

+X is forward, +Y is left, +heading is counter-clockwise
  • +X → forward  (driving forward makes x go up)
  • +Y → left  (strafing left makes y go up; right makes it go down)
  • heading 0 = facing +X, and turning counter-clockwise makes heading go up

This is why last lesson's pod fix mattered: if +Y pointed the wrong way, every path would steer sideways into a wall. Same frame, now used to give orders instead of just to read.

setStartingPose: place the robot, then tell the code

Before a match you physically set the robot down on the field, then call follower.setStartingPose(startPose) to tell it exactly where that is. From that moment its tracked position is in field inches. If the pose you type does not match where you set the robot, every path is shifted by the difference — so this one line matters.

Part A — Draw the path

A path is a list of poses joined by straight lines. A BezierLine is a straight path from one pose to the next, and a PathChain bundles it up for the Follower. You will build two chains: one to drive forward, and one to strafe left.

▸ SimpleAuto.java : SimpleAuto : Paths
Type this into SimpleAuto.java⩢ Copy
// Each spot on the field is a Pose(x, y, headingRadians).
Pose startPose = new Pose(START_X_IN, START_Y_IN, Math.toRadians(START_HEADING_DEG));
Pose pose1 = new Pose(12.0, -36.0, Math.toRadians(0.0));   // 48" straight forward (+X)
Pose pose2 = new Pose(12.0,  12.0, Math.toRadians(0.0));   // then 48" to the left (+Y)

// A BezierLine is a straight path; a PathChain wraps it for the Follower.
// Keep the heading constant so the robot faces the same way the whole time.
PathChain chain1 = follower.pathBuilder()
        .addPath(new BezierLine(startPose, pose1))
        .setConstantHeadingInterpolation(Math.toRadians(START_HEADING_DEG))
        .build();

PathChain chain2 = follower.pathBuilder()
        .addPath(new BezierLine(pose1, pose2))
        .setConstantHeadingInterpolation(Math.toRadians(START_HEADING_DEG))
        .build();
Heading in radians, not degrees

A Pose wants its heading in radians, the unit the driving math prefers. You think in degrees, so write Math.toRadians(0.0) and let Java convert. Same trick you used for telemetry, just the other direction.

Part B — Run the plan

Now sequence the match. Seed the start pose, follow chain 1, dump, then follow chain 2. The key pattern is the follow-and-wait loop: after followPath(...) you keep pumping follower.update() (to drive) and robot.update() (to keep mechanisms alive) until the Follower says it is no longer busy.

▸ SimpleAuto.java : SimpleAuto : Run
Type this into SimpleAuto.java⩢ Copy
// Tell the localizer where the robot is starting (field inches from here on).
follower.setStartingPose(startPose);

// Segment 1: drive forward to pose1.
follower.followPath(chain1, SPEED, true);
while (opModeIsActive() && follower.isBusy()) {
    follower.update();   // drive one step along the path
    robot.update();      // keep the mechanisms' state machines alive
}

// Action: dump, then WAIT for the dump to finish (pump both, never sleep).
robot.dumper.dump();
while (opModeIsActive() && robot.dumper.isBusy()) {
    robot.update();      // advance the dumper's state machine
    follower.update();   // hold position while dumping
}

// Segment 2: strafe left to pose2.
follower.followPath(chain2, SPEED, true);
while (opModeIsActive() && follower.isBusy()) {
    follower.update();
    robot.update();
}
The follow-and-wait loop is just the scheduler again

You never call sleep(). Instead you take thousands of tiny steps: each follower.update() nudges the wheels a little and re-checks the position, and each robot.update() advances the dumper a little. When the Follower reaches the target it reports isBusy() == false and the loop ends — the exact same “lots of small steps, never one big freeze” rhythm you have used all along.

⚠ Using a real robot? Do this first

If you have ever deployed Pedro Pathing to this robot from Android Studio (a Pedro line in your build.gradle), remove that dependency, rebuild, and re-install the Robot Controller app before you deploy this lesson. Otherwise the robot ends up with two copies of Pedro — the one baked into your app and the one this tool uploads — and the on-robot build fails with a duplicate-class error. From here on, let OnBot Java (this tool) be the one source of Pedro. Earlier lessons never touched Pedro, so this only matters now. In the simulator there is nothing to do.
