The Extractor Arm: A Two-Position Servo

Some robots carry a pollen extractor arm. It rides up, tucked out of the way, and when the driver wants it, it lowers in front of the robot. When the job is done, it goes back up. The driver decides when: D-pad down lowers it, D-pad up raises it.

It sounds simple, and it is — which makes it the perfect place to practice reading code carefully. This lesson reuses ideas you already know (enums, switch, named constants, subsystems, positional servos) and asks you to explain exactly what each line does.

Not every robot has an extractor, but everyone takes this lesson: “a servo with a few named positions” is one of the most common mechanisms in FTC. Like the last few lessons, you won't change any code here.

1. Two positions, two names

The arm can be in exactly two places:

  • STOWED — up and tucked in. This is where it starts every match.
  • DEPLOYED — lowered in front of the robot, ready to work.

You've seen this before. In the intake lesson, the roller could be FORWARD, OFF or REVERSE, and we listed those choices in an enum. The arm gets one too:

public enum State {
    STOWED,     // up, tucked in -- where it starts
    DEPLOYED    // lowered in front of the robot
}
Enum refresher
  • An enum is a fixed list of named choices. A variable of type State can only ever be State.STOWED or State.DEPLOYED — nothing else, no typos, no mystery numbers.
  • Why not just a boolean deployed? It would work for two positions. But State.DEPLOYED reads like English, telemetry prints its name (“DEPLOYED”) instead of “true”, and if your team later wants a third position (say HALFWAY), you add one word to the list.
  • It's public so the TeleOp can name the type (Extractor.State) to show it on the Driver Hub.

2. Arm positions vs. servo numbers

The servo doesn't know the words “stowed” and “deployed”. It only understands a number from 0.0 to 1.0. So we give each state its own number, as named constants:

private static final double STOWED_POS   = 0.10;   // servo number for "up"
private static final double DEPLOYED_POS = 0.75;   // servo number for "down"
  • private — only the Extractor class needs these numbers. Nobody else can see or change them.
  • static — they belong to the class itself; there's just one copy.
  • final — once set, they never change while the program runs.

Writing STOWED_POS instead of 0.10 everywhere means that when you re-tune the arm, you change one line, and the code still explains itself. A bare 0.10 in the middle of the code is called a magic number: it works, but nobody remembers why.

3. The subsystem: commands and update()

Extractor has the same shape as every subsystem you've built. One field remembers what we want:

private State state = State.STOWED;   // starts stowed

The commands only change that field. They don't touch the servo:

public void deploy() {
    state = State.DEPLOYED;
}

public void stow() {
    state = State.STOWED;
}

And update(), which the scheduler calls every loop, turns the state into a servo number with a switch, exactly like the intake turned its state into motor power:

@Override
public void update() {
    if (servo == null) {
        return;                              // no extractor on this robot
    }
    switch (state) {
        case STOWED:
            servo.setPosition(STOWED_POS);
            break;
        case DEPLOYED:
            servo.setPosition(DEPLOYED_POS);
            break;
    }
}
Read it like a sentence

“Every loop: if there's no extractor servo, stop. Otherwise, look at the state. If it's STOWED, send the stowed number. If it's DEPLOYED, send the deployed number.” The break after each case means “done, leave the switch”; without it, Java would fall through and run the next case too.

Two small “getter” methods let other code ask about the arm without being able to change it directly:

public State getState() {
    return state;
}

public boolean isDeployed() {
    return state == State.DEPLOYED;
}

Notice == (two equals signs) compares: “is the state DEPLOYED?” gives back true or false. A single = assigns, like in deploy().

4. The buttons: D-pad down and up

In your TeleOp loop, two lines hook the D-pad to the commands:

if (gamepad1.dpad_down) robot.extractor.deploy();
if (gamepad1.dpad_up)   robot.extractor.stow();

Down lowers the arm, up raises it. The button matches the motion, so drivers don't have to think about it. In the simulator, the ; key is D-pad up and / is D-pad down.

Why two buttons and no edge detection?

In the intake lesson, pressing A toggled the roller, so we needed edge detection: holding A for 20 loops would otherwise flip it on and off 20 times. Here each button always means the same thing. Holding D-pad down for 20 loops just says “deploy” 20 times, and the arm is already deployed after the first one. Nothing flips, so no edge detection is needed. And the driver never has to remember which way the arm is right now: up is always up.

5. How is this different from the old dumper?

An earlier version of this course had a dumper: one press ran a whole timed sequence (raise, hold for two seconds, lower), using a stopwatch and four states. That's the right tool when a mechanism should run a routine on its own.

The extractor is the opposite: the driver decides how long it stays down. Lowered during a pickup, raised the moment the driver is done. No timers, no extra states, just two positions and two buttons. Picking the simplest design that does the job is a big part of engineering.

6. Safety and robots without an arm

The constructor finds the servo and puts it in the stowed position right away:

public Extractor(HardwareMap hardwareMap) {
    Servo found = null;
    try {
        found = hardwareMap.get(Servo.class, "extractor");
    } catch (IllegalArgumentException e) {
        found = null;   // no "extractor" in the configuration -- run without it
    }
    servo = found;
    if (servo != null) {
        servo.setPosition(STOWED_POS);   // moves as soon as INIT runs -- hands clear!
    }
}
  • It moves at INIT. A positional servo jumps to its position the moment the code starts. Keep hands clear of the arm when you press INIT.
  • try / catch. If the robot has no servo named extractor, hardwareMap.get throws an error. The catch “catches” it, we store null, and the rest of the robot keeps working. That's why update() starts with if (servo == null) return;.
  • Wrong direction? If down and up are backwards, add servo.setDirection(Servo.Direction.REVERSE); in the constructor, or swap the two numbers.

7. Finding your two numbers

The numbers 0.10 and 0.75 are only placeholders. Every robot's arm is mounted a little differently, so you measure yours. The reward includes a small tool OpMode, Extractor Calibrate, that lets you move the servo with the right stick and shows its number on the Driver Hub:

  1. Run Extractor Calibrate. (Hands clear: the arm moves to the middle at START.)
  2. Slowly move the arm with the right stick to the perfect up spot. Write down the number.
  3. Move it to the perfect down spot. Write that number down too.
  4. Put them into STOWED_POS and DEPLOYED_POS.

Using telemetry to measure the real robot, then writing the result into a named constant, is how almost every mechanism in FTC gets tuned.
