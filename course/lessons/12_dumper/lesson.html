A Timed Machine: The Dumper

You just built the intake — a state machine whose states were instant: the moment you pressed a button, the motor changed. Now you'll build the dumper, the servo that tilts a bucket up to score the game pieces your intake collected. It follows the exact same four-part shape you already know — but with one powerful new idea: its states are timed.

What does the dumper do?

One press of a button should run a whole little sequence: raise the bucket, hold it up for a moment so the pieces slide out, then lower it back to level. The driver presses once and keeps driving — the dumper finishes the routine on its own.

The trap: sleep()

The obvious way to write “raise, wait, lower” looks like this:

Do NOT do this
servo.setPosition(UP);
sleep(2000);            // <-- freezes the WHOLE robot for 2 seconds
servo.setPosition(DOWN);

That sleep(2000) freezes everything for two seconds: the driver can't steer, the intake can't run, telemetry stops updating. In a match that's a disaster. We need to wait without stopping the world.

The fix: a state machine + a stopwatch

A servo takes real time to travel, so “raising” and “lowering” become their own states. We keep a field for the current state, and an ElapsedTime stopwatch that tells us how long we've been in it. Each loop, update() peeks at the stopwatch and, when a step's time is up, moves to the next state — then returns immediately. The robot never freezes; the driver keeps full control the entire time.

Same four parts as the intake — states, a current-state field, a command, and an update() — you'll just add a stopwatch to the mix.

Meet Dumper.java

A new file appeared: Dumper.java. Open it and read the top. The tuning constants (servo positions and step timings), the servo field, the timer stopwatch, and the constructor are already there. What's missing is the state machine — you'll add it in the same four parts as before.

Reversing a servo (just like a drive motor)

Remember reversing a drive motor so “forward” spun the right way? A servo can be reversed the exact same way. In the constructor you'll see servo.setDirection(Servo.Direction.REVERSE). We use it here so that a bigger position number tilts the bucket up to dump.

There's one twist a motor doesn't have: reversing a servo mirrors every position around 0.5 — a command of p now lands where 1 - p used to. So after reversing you re-tune the two numbers by testing on the bot: here CARRY_POSITION = 0.1 holds the bucket level (stowed), and DUMP_POSITION = 0.8 tilts it up to dump. If your real robot tilts the wrong way, flip that one line and re-tune these two numbers — no rewiring, no remounting.

Part A — Name the states (an enum)

The intake had three states. The dumper has four, because moving takes time: it's STOWED at rest, RAISING while the servo travels up, DUMPING while it holds at the top, and LOWERING while it travels back down.

▸ Dumper.java : Dumper : States
Type this into Dumper.java⩢ Copy
public enum State {
    STOWED,    // resting, bucket level -- the normal state
    RAISING,   // servo commanded up; waiting for it to reach the top
    DUMPING,   // holding at the top so game pieces slide out
    LOWERING   // servo commanded down; waiting for it to reach level
}

Now add the field that remembers the current state. It starts STOWED — the bucket should be at rest when the robot boots.

▸ Dumper.java : Dumper : Current State
Type this into Dumper.java⩢ Copy
private State state = State.STOWED;   // start at rest

Part B — The command: dump()

Here's the key difference from the intake. dump() does not run the whole sequence — it only starts it. It commands the servo up, resets the stopwatch, and switches to RAISING. Then it returns instantly. The waiting happens later, in update(). The state == STOWED guard means pressing the button again mid-dump is ignored, so a cycle in progress is never interrupted.

▸ Dumper.java : Dumper : Command
Type this into Dumper.java⩢ Copy
public void dump() {
    if (state == State.STOWED && servo != null) {
        servo.setPosition(DUMP_POSITION);
        timer.reset();
        state = State.RAISING;
    }
}

public boolean isBusy() {
    return state != State.STOWED;
}

public State getState() {
    return state;
}
Why servo != null?

The constructor sets servo to null if no dump_servo is in the robot config, so this check just means “a robot without a dump servo does nothing here instead of crashing.” isBusy() reports whether a cycle is running (autonomous will wait on it later), and getState() lets the OpMode show the state on the Driver Hub. Both are read-only windows — they never change the state.

Part C — update(): advance the timed sequence

This is where the non-blocking waiting lives. The scheduler calls update() every loop. It checks the stopwatch and, when the current step's time is up, moves to the next state (commanding the servo if needed) and resets the stopwatch — then falls straight through and returns. Read it as a chain: RAISING finishes → hold; DUMPING finishes → lower; LOWERING finishes → done.

▸ Dumper.java : Dumper : Advance
Type this into Dumper.java⩢ Copy
switch (state) {
    case RAISING:
        if (timer.milliseconds() > RAISE_TIME_MS) {
            timer.reset();
            state = State.DUMPING;
        }
        break;

    case DUMPING:
        if (timer.milliseconds() > HOLD_TIME_MS) {
            if (servo != null) {
                servo.setPosition(CARRY_POSITION);
            }
            timer.reset();
            state = State.LOWERING;
        }
        break;

    case LOWERING:
        if (timer.milliseconds() > LOWER_TIME_MS) {
            state = State.STOWED;
        }
        break;

    case STOWED:
        break;
}

Notice the servo is commanded in exactly two places — up in dump(), down here in DUMPING — and the timings all come from the named constants at the top. Bucket too slow? Make RAISE_TIME_MS bigger. Pieces not falling out? Make HOLD_TIME_MS bigger. One place each.

Part E — Fire it with the Y button

One press should run the whole cycle, so we use edge detection again — act only on the loop where Y first goes down. But this time there's no toggle: dump() guards itself, so a press during a cycle is simply ignored.

1. Remember last loop's button

▸ MecanumDrive.java : Dumper : Variables
Type this into MecanumDrive.java⩢ Copy
private boolean previousY = false;

2. In the loop: on a fresh Y press, start the dump

▸ MecanumDrive.java : Dumper : Loop
Type this into MecanumDrive.java⩢ Copy
boolean pressedY = gamepad1.y && !previousY;
if (pressedY) {
    robot.dumper.dump();
}
previousY = gamepad1.y;

That's the whole control: one call to dump(). The OpMode never touches the servo or the timer — it just fires the command and keeps driving while the dumper runs its routine in the background.

Optional: watch the state flip live

Near your other telemetry.addData(…) lines you can add telemetry.addData("Dumper", robot.dumper.getState()); to see it step through RAISING → DUMPING → LOWERING → STOWED on one press — proof the sequence runs without ever blocking your driving.
